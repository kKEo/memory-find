# Eval report — v1.1.0 (P7: entities and graph, as an index)

*Measured 2026-10-03 with the deterministic hash embedder (the CI gate), `default` profile.
New in this report: a platform namespace with a three-link chain of services for the multi-hop
slice, two single-hop controls in the same namespace, planted alias pairs for merge precision,
and a graph-tax column. The baseline was re-recorded because the query set grew.*

## The P7 gate (knowledge-base corpus, ablation profiles)

| profile | arms | all nDCG@10 | multi-hop nDCG@10 | multi-hop MRR | lookup nDCG@10 | exact | graph ms (when run) |
|---|---|---|---|---|---|---|---|

| no-graph | text-only + entity | 0.869 | 0.513 | 0.415 | 0.667 | 1.000 | 0.1 |

| minmax | default with score fusion | 0.881 | – | – | – | – | 0.2 |

Pre-registered gate: the graph arm stays on by default in `auto` only if it adds at least 0.05
nDCG@10 on the multi-hop slice with no single-hop category losing more than the tolerance.
Result: +0.17 over the entity arm alone (+0.25 over the 1.0 arms); lookup and exact unchanged.
`GraphAuto` is on. Graph weight: a sweep over 0.3 / 0.5 / 0.8 / 1.2 gave multi-hop nDCG 0.59 /
0.68 / 0.68 / 0.72 with no change elsewhere; 0.5 was chosen as the lowest value that reaches the
plateau, on three planted queries, so it is a starting point and is written as such in the
profile derivation.

Per query:

| query | relevant | text-only nDCG | default nDCG | what the graph did |
|---|---|---|---|---|
| multihop-connect-change | the v1.8 Connect page | 1.00 | 1.00 | routed in; agreed with the text arms |
| multihop-billing-replication | Ledger Store page (names only one of the two entities) | 0.39 | 0.39 | found it at rank 2 in its own list; four pages that name the asked entities directly still outrank it |
| multihop-billing-nodes | Quorum Replication and Ledger Store pages (two links from the named entity) | 0.48 | 0.85 | single seed: both pages are what the walk reports, and nothing else does |
| multihop-ledger-mailer | Billing page (bridge between the two named entities) | 0.50 | 0.50 | rank 2 in the graph list; the two pages *about* the named entities keep rank 1 and 2 |

Honest reading: the graph arm finds the bridge page every time, but when the question names two
entities, the pages about those entities also match by words and meaning, and rank fusion keeps
them ahead. The gain is in recall@5 (0.63 → 1.00 on the slice) and in the single-seed relational
question. Getting the bridge to rank 1 would need a fusion rule that trusts agreement between the
walks more than agreement between text arms; that is a 1.x experiment, pre-registered here, not
a tuning done on these three queries.

## Side findings fixed in this phase

| Finding | Effect | Fix |
|---|---|---|
| The default profile had no weight for the fact arm, so facts voted with weight 0 since v0.8.0 | fact-key and knowledge-update slices passed through the keyword arm; the derivation claimed 0.4 | weight 0.4 added; the profile printout now shows it |
| With the weight on, a fact matching one common word ("context") outranked the right passage on `mood-burnout` | notes nDCG would have dropped 0.04 | a keyword-only fact hit must cover at least half the query's content words |
| An always-on entity arm regressed `postgres-index` and two more lookups: "Postgres" is an entity, and pages mentioning it outvoted the page answering the question | lookup nDCG 0.994 → 0.935 | both structural arms are routed by one rule (two or more known entities, or relational phrasing with one) |
| Number-suffixed identifiers (quorum.Publish7 vs quorum.Publish10) flooded the merge queue: 213 candidates, 1 correct | merge precision 0.005 | names differing in a number are different things; queue now 2 candidates, both correct |
